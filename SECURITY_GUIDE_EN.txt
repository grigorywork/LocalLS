SECURITY UPDATE (October 9, 2026)

LocalLS supports SSH private-key authentication. A user identity key grants
login; a server host key identifies the server. They are different keys.

MIGRATE WITHOUT LOSING ACCESS
1. Update over the existing installation, keeping app data.
2. Connect with the existing credentials and verify the server fingerprint.
3. Open Settings → Security / SSH key (Russian UI: Безопасность / SSH-ключ).
   On Android this is inside application settings. Generate RSA 3072 or import
   an existing private key with its passphrase if encrypted.
4. On Windows/Fedora enable Save secrets in Connection and save settings first.
   Persistence requires working OS encryption. Otherwise generated keys remain
   only in memory until full exit. If the keyring is unavailable, import a key
   you already own and keep the original file protected with a passphrase and
   suitable filesystem permissions. Android uses Android Keystore encryption.
5. In Security enter the current server password in the one-time installation
   field and click Install key and verify login. Confirm host and account.
6. LocalLS appends the public key to ~/.ssh/authorized_keys, preserving existing
   entries, and sets .ssh to 700 and authorized_keys to 600. It opens a fresh
   key-only connection. Only after that succeeds does the client select key
   authentication and remove the stored password for this profile.
7. Reconnect, browse SFTP and transfer a test file.
8. Repeat for every device. Prefer a separate identity per device for revocation.
9. Verify after fully exiting and reopening LocalLS. Do not disable server
   passwords before this succeeds and you have another working way to access
   the server directly.

Key mode fails closed for a missing/wrong key; it never falls back to a password.
Password mode is available for an explicit migration while the server permits it.
Export .pub contains only public material. Public profile export does not transfer
private keys, passphrases, passwords or agent tokens. Create/import and enroll
an identity separately on the receiving device. Removing the local identity does
not revoke it remotely: remove its authorized_keys line while keeping other keys.
Uninstalling/resetting Android can destroy its Keystore identity; establish
another tested login first. Private-key export is not implemented in this release.

CONTROL AGENT: HTTPS
SSH/SFTP works without an agent. An independent agent provides SSH service
start/stop/restart, including when SSH is down. Agent 0.3 uses TLS 1.2+ and a
random Bearer token. Download LocalLS-Agent-0.3.zip separately from the new
release and extract it on the server phone. Back up the previous configuration.
In Termux run ./install.sh from the extracted folder. It preserves the existing
token, bind address, port and boot scheme, creates an RSA 3072 certificate and
prints its SHA-256 fingerprint. Never post the token output in logs or issues.
The installer does not restart an existing agent process. Stop that particular
old process using the existing method and start the updated one manually.
Do not run two agents on the same port or disturb the running sshd.
Keep the original agent port/token in LocalLS. In Security choose Check agent
HTTPS certificate, compare SHA-256 with the server, then confirm trust.
The bootstrap request sends no token. Requests are blocked until trust exists;
a substituted certificate also blocks requests. Check replacements independently.
Certificates expire after 365 days; renew in advance and confirm the new pin.
Self-signed TLS is trusted by the exact certificate fingerprint. Initial trust
still depends on your independent verification, even on a home network.
Old HTTP agents need explicit temporary compatibility; the app asks confirmation
because tokens then travel without TLS. This option is off by default. Keep it
off with a new HTTPS agent.

SERVER PASSWORD POLICY
This update does not automatically disable server passwords or modify sshd_config,
SSH ports or sshd startup mechanisms. A key-only client does not prevent another
client from authenticating with a password while the server still allows it.
After testing every identity, an administrator can separately enforce:
  PubkeyAuthentication yes
  PasswordAuthentication no
  KbdInteractiveAuthentication no
  AuthenticationMethods publickey
Termux usually uses $PREFIX/etc/ssh/sshd_config; Fedora uses /etc/ssh/sshd_config
and included files. Back up configuration, inspect Include/Match, run sshd -t
before applying, and inspect effective sshd -T settings for the target account
and address. Apply via the existing service mechanism with a backup session,
then test a fresh connection. Administrative privileges depend on the server OS.
Do not copy these settings blindly or close the only working session first.

NETWORK EXPOSURE
Outbound internet for server updates is different from inbound public access.
Moving SSH from port 22 to 8022 is not a substitute for keys and a firewall.
Avoid router port forwarding; check UPnP and IPv6 firewall rules. IPv6 may lack
NAT protection. For remote access prefer Tailscale with restricted grants/ACL,
verified devices and a protected account. Fedora's Open SSH firewall action
allows the service in the current zone; it does not automatically restrict it
to your home subnet. Review the zone, interface and allowed sources in Fedora.
This build environment did not verify the public reachability of your server.
Never publish private keys, tokens, personal profiles or agent configuration.
