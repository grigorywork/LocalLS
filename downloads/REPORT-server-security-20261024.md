# LocalLS — проверка атак и исправления безопасности, 24 октября 2026

Проверен встроенный Android SFTP-сервер текущей рабочей версии. Атаки выполнялись только на одноразовых локальных экземплярах с тестовыми ключами и файлами. Физический телефон пользователя и его сеть не атаковали. Это проверка перечисленных сценариев, не доказательство отсутствия всех возможных уязвимостей.

## Найдено и исправлено

1. **Исчерпание файловых дескрипторов авторизованным устройством.** До исправления библиотечный предел открытых handles составлял 2147483646. Ограниченный тест подтвердил открытие сверх16 файлов в канале и сверх32 файлов/каталогов одним устройством через разные соединения. Теперь допускается16 handles на канал и32 на ключ устройства суммарно по всем каналам/соединениям; для7 устройств это максимум224 удерживаемых удалённых handles. Отказ происходит до открытия/CREATE/TRUNCATE, поэтому превышение квоты не обнуляет существующий файл. Квота освобождается после закрытия, ошибочного открытия и разрыва соединения. Служебные временные каналы без удалённого handle не учитываются как удерживаемые клиентом; они ограничены числом работников подсистемы и закрываются внутри операции. Метаданные и хеширование файла не съедают квоту постоянных handles — это проверено отдельно. Другое устройство продолжает читать контрольный файл при заполненной квоте атакующего.
2. **Непроверенная длина и очередь пакетов SFTP.** Заголовок с объявленной длиной2147483647 удерживал канал в ожидании тела. Новый BoundedSftpSubsystem проверяет длину до удержания тела/постановки работы: от5 до263168 байт; максимум128 ожидающих запросов. Неверный размер и переполнение очереди закрывают атакующий канал. Заголовки могут приходить частями, несколько запросов — одним блоком. Обычный pipeline64 и полный WRITE с256КиБ данных проверены побайтно. Не утверждается, что сам заголовок с большой длиной немедленно выделял2ГБ: до исправления подтверждено именно удержание незавершённого канала.

3. **Устаревшая подпись RSA/SHA-1.** Уточнённый тест без клиентского ключа и запроса авторизации подтвердил, что прежний сервер согласовывал этот алгоритм. Теперь ssh-rsa/SHA-1 и устаревшие DSA signatures исключены из списка; сохранённый RSA3072 host key продолжает работать с RSA/SHA-2. Ключ, fingerprint, QR и настройки не меняются. CBC и DH group1 также проверены отдельными предложениями до авторизации и отклоняются прежними безопасными настройками. Это устранение устаревшего алгоритма, не доказанный взлом RSA-ключа.

Первые два случая требуют действующего разрешённого ключа; получение чужого доступа/чтение вне папки ими не подтверждено. Лимит очереди — дополнительное ограничение нагрузки. Новые атакующие тесты не отключались, прежние проверки не ослаблялись.

## Выполненные сценарии

- Вход без авторизации, пароль, неверное имя, неизвестный ключ; доступ к SFTP и обоим статусным подсистемам до SSH-аутентификации.
- Копирование публичного ключа с подписью другим приватным ключом; неправильный pin/nonce QR, истёкшее и заменённое приглашение, подмена устройства перед подтверждением. Закрытие QR и перезапуск не отзывают уже сохранённый разрешённый ключ.
- Отзыв ключа с закрытием его активной сессии; прежний QR не возобновляет отозванный доступ. Восьмое устройство не вытесняет семь разрешённых.
- Подмена host key до передачи клиентского удостоверения; попытка согласовать RSA/SHA-1 отклонена при сохранении работы прежнего RSA-ключа с современным алгоритмом.
- Чтение/удаление за пределами общей папки через dot-dot, абсолютный путь, ссылку наружу, NUL, обратную косую черту и percent-encoding; запись/переименование через ссылку наружу; создание symlink/hardlink.
- SSH shell/exec, прямые и обратные TCP-туннели заблокированы; телеметрия доступна только после входа по ключу.
- Повреждённые SSH-баннеры/пакеты, неизвестная SFTP-команда, отсутствующие поля, невозможная длина строки, нулевая/отрицательная/чрезмерная длина пакета, переполнение очереди при контролируемо задержанной операции.
- Ограниченный всплеск40 неавторизованных TCP-соединений: действующая сессия продолжает читать неизменённый файл; после закрытия всплеска новый вход работает. Это не нагрузочное доказательство устойчивости к длительному распределённому DoS.
- Обычная работа:7 различных клиентов, Android/Node desktop QR interoperability, независимый OpenSSH, чтение/запись, Unicode, продолжение передач, отмена, сохранение прежнего файла при конфликте/ошибке.
- Существующие Python HTTPS-agent тесты: запрет токена/HTTP без согласия, неправильный токен, TLS и приватные права файлов. Это не полный пентест отдельного Termux Agent.

## Практические границы

Клиенты с разрешёнными ключами имеют общий доступ на чтение/запись в папку сервера по текущей модели приложения: это не отдельные изолированные папки для каждого клиента. Владелец разрешённого ключа может удалить доступные ему файлы или заполнить общую папку. Лимиты handles/пакетов не являются дисковой квотой. При утрате устройства следует отозвать его ключ. Рутованное/скомпрометированное устройство, кража разблокированного телефона, длительная сетевая перегрузка и неизвестные ошибки ОС/криптобиблиотек остаются вне доказанной защиты этого стенда. На физическом телефоне эти проверки не выполнялись.
